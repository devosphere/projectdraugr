## Context — what today's review established

A live playthrough (Chronicle 9, "Wolf Kingdom", Days 1–10) was run in **Phase 0** — a single ChatGPT acting
as the whole engine over 13 hand-saved JSON files — and felt **richer and less restrictive** than the current
**Phase 1** deterministic engine, despite Phase 1 having a superior UI, real persistence, real physics, and no
hallucinated matter. The review of that database + the new GitHub issues (#29–#37) produced **DR-0022**. The
short version: Phase 1 is *sounder but thinner*, and the thinness is fixable **additively**, not by a rewrite.

### Why Phase 0 felt richer (and the corrected reading)
- It said **yes** to any rational action (a "recipe" there is just a *name*; crafting was improvised).
- Every **object was thick** — capabilities, dimensions, provenance (`tools_used`), and a dated
  `modifications` log (the Utility Belt went Revision I→II→III, each adding a tool holder).
- **Corrected principle (user, 2026-08-04):** the goal is **NOT** Phase 0's fuzzy resource pools. Phase 1's
  **exact numerical quantities stay.** The missing piece is **AI reasoning** that says *yes, that's rational*
  and then does the bookkeeping precisely — templates as guides, Architect authors, Auditor validates,
  persistence is numerically accurate. See DR-0022 principles 1–4.
- **Reachability principle (user, 2026-08-04):** an action may use everything **physically in reach** —
  carried, on the ground nearby, **in on-site storage**, and **tools in a nearby rack** — not just carried
  load. One unified model. See DR-0022 principle 2.

## The plan (layered; deterministic first, AI-on after)

### Layer 1 — Unified reachability *(deterministic, key-free)* — ✅ COMPLETE (commit pending)
- [x] One reachability model = carried + nested-in-carried + loose-at-location + **contents of containers/storage sited at the location**, for **materials and tools**. Shipped as `PhysicalItemService.REACHABLE_CTE` (roots at carried ∪ location-sited; descends `item_containment` from both). Fixes F3/F4 and the stone-shelf limitation.
- [x] Routed **every** input-sourcing + tool + grade path through it: `hasAtLeast`, `hasAtLeastHere`, `consumeOne`, `consumeOneHere`, `reachableItemKeys`, `reachableFoods`, `worstGradeAmong`, `findReachable`, and tool checks (`hasCuttingTool`/STRIKING/AXE via `hasAtLeast`). The inventory/HUD/carry-capacity view stays carried-only by design.
- [x] Regression: `tests/regression/reachability-onsite-storage.sql` seeds an on-site bin (5 dry_branch) + a rack (stone_knife) + a ground fibre + a carried vine against the real schema and asserts all are in reach. Full backend suite 142 green.
- [ ] **Deferred to Layer 4b:** scope reachability to the current **zone** (not the whole chunk) once multi-zone settlements exist — a tool is reachable because you're at *that* workstation, not merely in the chunk. **Counts + source surfaced to the AI context is Layer 3.**

### Layer 2 — Make perception reveal the world *(2a deterministic; 2b AI-enriched)*
- [x] **2a** — `ExaminationService.presentLife(chunk, acuity)`: names the *actual* life present — flora (`chunk_flora`), wildlife (`wildlife_population` via `ecology_site`), fish (aquatic species by biome), insects (`insect_colony`) — scaled by acuity (attention + perception mastery): the conspicuous are seen, the shy read from sign, a keener eye names more. Wired into **OBSERVE** (`survey()`) and the **examination verbs** (INSPECT/ANALYZE/INVESTIGATE of a place). Fixes F5, #33, and the "can't hunt what you can't see" core of #37. All four queries validated against the real schema; 142 backend tests green. *(Deferred to Layer 3/enrichment: naming stored materials in on-site containers explicitly, and TRACK enrichment — TRACK already surfaces sign via `WildlifeEncounterService.track`.)*
- [ ] **2b** *(AI-on)* deepest examination tier enriched by the Narrator, non-load-bearing.

### Layer 3 — Quantified, sourced AI context + templates as exemplars *(built on Layer 1)*
- [ ] Interpreter/Architect receive the **quantified, sourced** reachable pool (counts + where), not bare keys.
- [ ] Feed the **130 processes as exemplars** into the Interpreter/Architect prompts (the "templates as guides" of DR-0022 §3), so authored recipes look like real ones (proper inputs, tool, mass-balanced output).
- [ ] Miss path stops returning the ambiguous one-liner when the pipeline is available; engages Interpreter→Architect.
- [ ] **AI-reasoning quality is its own engineered workstream** — the full plan (validated-schema output, prompt caching, the offline **golden-set eval harness**, the measured **model-tier frontier**, author↔critic-loop tuning, dedup, Overseer telemetry, and the eval→fix loop) is specified in **[runtime-procedure-authoring.md → "AI reasoning quality"](../architecture/runtime-procedure-authoring.md#ai-reasoning-quality--making-it-good-cheap-and-measurable)**. Build the eval harness *before* the live keyed run so tuning is offline, auto-scored, and cheap.
- [ ] **Interpreter convergence (F9) — make the recurring cost amortize.** Memoize every resolved miss so the second occurrence is free: a successful composition persists a scoped **keyword/alias → plan** (recommended; rides the promotion pipeline); the **Auditor** validates it and surfaces it for canon promotion (same path as an authored mechanic); a **deterministic pre-filter** resolves near-misses with no AI call. Without this the Interpreter re-pays for every rephrasing. See [Cost model & role economics](../architecture/runtime-procedure-authoring.md#cost-model--role-economics-pay-once-then-free).
- [ ] **Enforce the hand-off contract** — classifier does max free work → Interpreter emits a *complete* composition-plan or authoring-brief → Architect **formalizes** (never re-reasons) → QA judges plausibility only → **Auditor validates the persisted rows and drives canon promotion** (Architect mechanics AND Interpreter aliases, human-approved). Each role adds narrow value over the prior's structured output; **no role re-derives the player's intent.** This is what keeps authoring a discovery from spiking cost. Contract table in the spec.

### Layer 4 — Thick objects (additive attribute layer) *(deterministic schema; author fills it)* — ✅ deterministic parts COMPLETE
- [x] **`V68`** additive `object_attribute` (key/value features) + `object_modification` (dated improvement log) on `world_object` — **additive metadata, never an input to the physics gate**. Applies clean through the whole migration chain.
- [x] **REFINE** now records *what* changed as an `object_modification` note ("Added a stone hammer holder"), not just an anonymous revision bump — the Phase-0 Utility-Belt-Revision-III evolving-object richness.
- [x] **Examination surfaces it**: `inspectItem`/`investigateItem` read `object_attribute` (features) + `object_modification` (its later work), so an object reads as a bespoke, evolving thing.
- [ ] **AI-dependent (Layer 3):** the Architect populates `object_attribute` (handle, dimensions, capabilities) when authoring a bespoke item — needs the operator key.

### Layer 4b — Kingdom-building payoff: workstations + multi-zone settlements *(deterministic; found on review)*
This is the Phase-0 mid-game loop and it currently has **no mechanical existence** in Phase 1 (F7/F8).
- [ ] **Workstations as capability-enablers.** A completed workstation sited at the chronicle's zone **enables or improves** the relevant crafts: a woodworking table unlocks/【speeds/quality-boosts】woodworking processes, a stoneworking table stone processes, a weaving/sewing table textiles, a knowledge workstation writing/mapping. Model: a process may declare a `requires_station` / `improved_by_station` tag; reachability (Layer 1) already knows what's sited at the zone. **This is what makes building a kingdom mean something.**
- [ ] **Multi-zone settlements.** Replace one-name-per-chunk (F8) with **many named zones per location** (`chronicle_named_location` keyed per-zone, not per-chunk): districts, storage bins, drinking area, tool shed. Storage/racks live *in* a zone; reachability is zone-scoped. This is also the substrate Layer 1 needs to say "the tool is on the rack in this zone."
- [ ] **Plan → operational lifecycle.** A zone/structure can be **planned** (named, blueprinted) before it is **built/operational** — the Phase-0 loop (Warehouse District: Planned; Heavy Manufacturing: Operational). Additive status on the zone/construction record.
- [ ] **EXCEED check:** Phase 0 tracked all this in free-text JSON that could contradict itself. Phase 1 must make zones/workstations **first-class, referential, and consistent** (a workstation that enables a craft is verified to exist and be complete; a stored tool is really in that zone).

### Layer 4c — Documents & maps that actually read back (#33-adjacent)
- [ ] Verify/repair the read path: `literature_revision.content` **is** stored and `readRevision` returns it, yet the playthrough hit "view content returned nothing." Establish whether the map's content was empty, unreachable, or a UI gap, and fix so fetched maps/records render their full content (Phase 0 embedded whole ASCII maps).
- [ ] **EXCEED check:** Phase 1 maps are generated from real geography/discovery data (accuracy, revisions, deterministic omissions) — richer and truthful vs Phase 0's hand-typed ASCII. Make sure that richness is actually surfaced on read.

### Layer 5 — Richer narration templates (#30)
- [ ] Rework base templates into a multi-block, 3–5 sentence frame (Progression / Observation / …) built on the existing `PerceptionFrame` + `StateChange` deltas; lowers AI-narrator cost.

### Quick fixes (small, independent)
- [x] **#32** — `bath` added to WASH; DRINK/WASH now accept any reachable fresh water via `waterInReach()` (WETLAND, RIVER_BANK, or a freshwater spring/stream/river ecology site), not only WETLAND. Regression cases added.
- [x] **#36** — the FISH classifier no longer fires when the text is crafting a **net** (net + weave/craft/make/knot/braid/tie); "weave a fishing net" now falls through to the process/authoring path instead of the false "no water here". Regression cases added.

## The canonical acceptance example (the basket)

> Reachable (carried + on-site bins/racks): `dry_branch ×5`, `plant_fiber ×5`, `fiber_cordage ×2`, `vine ×3`,
> stone knife in the on-site Tool Shed. Action: *"weave a hand-carry basket with a handle — cut and bend the
> branches to a frame, weave fibre and vine across it, tie the handle with cordage."*

1. **Layer 1** makes all of the above reachable (branches on the ground, cordage in the fibre bin, knife in the rack).
2. **Interpreter** tries existing recipes → `weave_large_basket` (8 fibre + 8 vine) doesn't fit; no "with handle" variant.
3. **Architect** authors `hand_carry_basket_handled` ← `dry_branch ×3 + plant_fiber ×4 + fiber_cordage ×1 + vine ×2`, tool CUTTING, output mass ≤ input mass; attributes `{handle:true, dimensions:…, capabilities:[carry]}`.
4. **Gate** (mass/reachability) → **QA** (plausibility, ≤2 rounds) → `chronicle_tech_discovery` → **Auditor** validates.
5. **Execute** consumes exactly those counts; the basket persists with accurate numerical data and is grab-able later.

When this round-trips with the key on, the thread's core goal is met.

## Risks, unknowns, and the confidence gate

**Where I am NOT yet confident, stated plainly:**

1. **Nothing is built.** Plan-confidence ≠ build-confidence. A playthrough before Layers 1–4b ship will fail as #29–#37 did.
2. **AI-reasoning quality is iterative and key-dependent** — but now has a concrete, *offline* plan. The full engineering (validated-schema output, prompt caching, golden-set eval harness, measured model-tier frontier, loop tuning, dedup, telemetry) is in [runtime-procedure-authoring.md → "AI reasoning quality"](../architecture/runtime-procedure-authoring.md#ai-reasoning-quality--making-it-good-cheap-and-measurable). Key point: the gate makes weak output *rejected, not catastrophic*, and the eval harness makes tuning cheap/auto-scored so the expensive keyed run happens **once, at the end, against an already-tuned pipeline.** Still not one-shot — budget a handful of eval→fix iterations.
3. **Model-tier decision is unmade — and will be made on evidence, not guessed.** The eval harness measures the quality/cost frontier per role (run the Architect on the strongest model for the ceiling, step down until the acceptance suite breaks, pick the cheapest that still passes). Cost aligns with rarity — the expensive Architect/QA fire only on genuine novel authoring, then free after dedup/canonisation — so a strong Architect is affordable. Final tier choice (and subscription tiering) is the user's, informed by the eval numbers.
4. **Latency/cost per novel action.** Authoring is several sequential LLM calls (Interpreter → Architect → QA ≤2 rounds → Auditor). For a playthrough doing many novel things, that is slow and paid **the first time** for each mechanic (then free after canonisation). The loading overlay helps but the wait itself is a UX risk to "engaging."
5. **No live baseline.** Findings are code-read, not observed. Integration tests skip locally (Docker). We must boot the stack and measure current behaviour before/after.

**The confidence gate (do this BEFORE the user's real playthrough):**
- [ ] Ship Layers 1–4b (deterministic) and the quick fixes.
- [ ] Boot the stack; run the **acceptance suite A1–A10** deterministically; record pass/fail as the measured baseline→result.
- [ ] With the operator key, enable the AI switches; run A4/A5/A10 (the authoring cases) end-to-end; **iterate prompts** until they pass and read well.
- [ ] Only when the suite passes and reads richly do we tell the user "play." Until then, the honest status is *in progress, not ready*.

**Bottom line for the next cycle:** do not report "ready" on plan completion. Report "ready" only when the acceptance suite passes on a booted stack — deterministically for A1–A3/A6–A9, and through the tuned pipeline for A4/A5/A10.
